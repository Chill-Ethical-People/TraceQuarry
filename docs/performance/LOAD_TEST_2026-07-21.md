# TraceQuarry Capacity Test - 2026-07-21

## Executive Result

On an Apple M3 MacBook Air with 8 CPU cores, 16 GB RAM, Python 3.11, and local
SSD storage, TraceQuarry completed:

- one synthetic UAC archive containing 100,000 parsed events in 164.8 seconds;
- 500 synthetic UAC archives containing 50,000 combined events in 125.6 seconds;
- inventory of 1,000 native ESXi-style log files containing one million lines
  in 3.6 seconds.

The ESXi result is not parser support. TraceQuarry produced zero ESXi events and
classified all 1,000 files as unmatched. Native ESXi logs currently have an
operational parsing capacity of zero until dedicated source discovery and
parsers are implemented.

The recommended interactive ceiling on this machine is 50,000 total parsed
events. A 100,000-event collection is suitable for unattended batch use. The
200,000-event scenario exceeded the bounded 180-second test window at 1.4 GiB
RSS and was terminated; it is not a validated supported ceiling.

## Test Method

- Code baseline: commit `ae86bcd`, plus the local benchmark harness and an
  unrelated summary-preview counter correction.
- Harness: `tools/benchmark_capacity.py`.
- Evidence: deterministic synthetic text only, using reserved documentation IP
  ranges and no executable payloads.
- Input: `.tar.gz` archives, including multi-archive case workspaces.
- Incident window: the full synthetic year, causing both full and mini CSV and
  JSONL outputs to be written. This deliberately exercises a high-output case.
- Per-scenario safety ceiling: 180 seconds and 4 GiB resident memory.
- Each scenario ran in a fresh child process. Fixture generation was excluded
  from the measured interval.
- Raw measurements: `load-test-2026-07-21.json`.

| 10,000 | Passed | 6.8 s | 112 MiB | 36.9 MiB | 1,465 events/s |

| 100,000 | Passed | 164.8 s | 713 MiB | 367.1 MiB | 607 events/s |
| 200,000 | Timed out | 180.1 s | 1,436 MiB sampled | Incomplete | Not established |
| 400,000 | Skipped | - | - | - | Prior axis limit reached |

Successful single-collection runs produced approximately 3.85 KB of output per
event. Throughput declined as event volume increased, indicating that repeated
enrichment, sorting, deduplication, correlation, and serialization are more
important constraints than archive decompression alone.

## Capacity Guidance

### Recommended Operating Limits On This Host

- Interactive single collection: up to 50,000 parsed events.
- Unattended single-collection batch: up to 100,000 parsed events.
- Interactive case workspace: up to 100 collections and 20,000 combined events.
- Unattended case workspace: tested to 500 collections and 50,000 combined
  events.
- Large jobs: run one at a time, despite the GUI default of two concurrent jobs.
- Free storage: reserve at least 5 KB per expected single-collection event and
  12 KB per expected case event, plus archive expansion and safety margin.

These are tested and recommended bounds for this specific machine, evidence
shape, parser version, and output selection. They are not universal hard limits.
Longer lines, many IoCs, large bodyfiles, mixed parser types, and high finding
counts can reduce capacity.

### Existing Hard Safety Limits

- 100,000 archive members.
- 8 GiB total expanded archive size.
- 1 GiB maximum for one archive member.
- 8 GiB default web upload request.
- 40 GiB default web work-directory quota.
- Two concurrent GUI analysis slots by default.

The archive limits protect the analysis host. They should not be interpreted as
evidence that an 8 GiB expanded collection can be parsed within an interactive
response window.

## Engineering Recommendations

1. Add native ESXi discovery and parsers before advertising ESXi support,
   including rotated and compressed `vmkernel`, `hostd`, `vpxa`, `vobd`, `fdm`,
   shell, authentication, and lifecycle logs.
2. Stream normalized events to an indexed intermediate store rather than
   retaining and repeatedly copying the complete event list in memory.
3. Merge case timelines from per-host JSONL or an embedded database instead of
   retaining every collection analysis object through final case output.
4. Offer an output profile that avoids writing both full and mini CSV/JSONL when
   the incident window covers the complete timeline.
5. Compile and index detection rules once, then evaluate only rules relevant to
   each source or event action.
6. Add a GUI preflight estimate based on source count, expanded bytes, expected
   event count, free disk, and selected output formats.
7. Reduce concurrency automatically for large jobs and expose queued status in
   the Live Run panel.

## Reproduction

```bash
python3 tools/benchmark_capacity.py \
  --profile full \
  --work-dir /tmp/tracequarry-load-full \
  --timeout 180 \
  --max-rss-mib 4096
```

The work directory must not already exist. The harness stops later scenarios on
an axis after a timeout, memory-limit termination, or worker failure.
